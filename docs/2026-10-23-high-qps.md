# 有界并发采集与调参

## 配置与预算

默认保持 `qps=1.0`、`concurrency=1`、`batch_size=1`、`blocks_per_partition=500`。并发数必须是 1–128 的整数，布尔值和小数无效；QPS 必须有限且大于零。没有自动提压，也没有保证吞吐量。

在节点允许的前提下，可先明确试用以下设置：

```toml
qps = 500
concurrency = 32
batch_size = 20
blocks_per_partition = 500
```

16GB 主机可以从约 32 个工作线程开始观察，不应直接假设 128 安全。QPS 可以配置为更大有限正数；每次只提高一个参数，观察新处理区块速率、RPC 元素速率、429、重试、超时、RSS 和磁盘空间，再决定是否继续。只有吞吐改善且错误/资源可控时才保留调整。不能据这些试用参数承诺三个月窗口的完成时间。

共享 HTTP 客户端的连接池容量与最大同时在途 HTTP 请求数均为 `concurrency`。线程池在同一分片内重叠取完整区块与 receipts，运行中加已完成未消费区块最多为 `2 * concurrency`；分片规范化缓冲另计。该上限按区块计，不是严格字节/RSS 保证。协调线程按区块顺序校验、规范化和写入 SQLite/Parquet；不会并行提交多个分片。

QPS 是所有线程合计的逻辑 JSON-RPC 元素速率，重试再次扣预算，部分批次只扣重试的失败元素。发送前预留预算，空闲时间不累计突发额度。批请求中的元素仍会一起到达，不能把平均预算解读成严格无突发。HTTP 429 发布共享冷却，排队请求会复查延长后的冷却；已经在途的请求无法撤回。Retry-After 与重试次数沿用有界策略。

`batch_size` 主要影响不支持 `eth_getBlockReceipts` 时的逐交易 receipt 回退；支持整块 receipts 时每块一次该 RPC，不会因调大 batch 而自动批量获取多个区块。能力确认不支持后，后续工作跳过该方法；并发确认前可能已有不超过工作线程数的探测正在进行。`probe` 仍为有界能力样本，增大并发配置不会把它变成压力测试。

## 升级与同一运行恢复

1. 同步完整新版源码、工具及文档，保留服务器私有配置、数据和 checkpoint。安装环境沿用现有依赖，无需新服务或数据迁移。
2. 通过完整进程命令与 run ID 确认旧 collector 的 PID，只对确认的 PID 执行 `kill -TERM "$OLD_PID"`，等待其退出。不要同时启动第二个同 run 写入进程。
3. 在原配置中调整 QPS/并发数；保持 run ID、窗口、系统规则、分片大小和数据目录。运行 `.venv/bin/python -m pip install -e .` 后，以原命令恢复：

```bash
nohup .venv/bin/opbnb-activity collect --config config.toml --run-id full-2026q3 >>logs/collect.log 2>&1 &
tail -f logs/collect.log
```

`qps` 和 `concurrency` 均不参与结构身份计算，旧 manifest 没有并发字段时默认加载 1。恢复采集使用本次配置的并发/QPS；manifest 保留创建时的历史设置，启动日志显示本次实际设置。已有完整分片先复核校验和再跳过；不完整分片重新读取，不会重复累加交易。磁盘提交仍为原子分片，默认 SIGTERM 可立即终止，不能把它当作等待整片完成的优雅停机保证。应用内错误会停止补充任务、取消排队任务并等待运行中工作结束后再关闭客户端。应保留 Parquet、备份和 DuckDB spill 所需空间。

## 日志口径

原 `processed_blocks`、`committed_blocks`、`new_blocks`、区块速率和 ETA 的定义不变。新字段：

| 字段 | 范围/含义 |
| --- | --- |
| `concurrency` | 当前运行配置上限 |
| `scheduled_blocks` | 已提交且尚未被协调线程消费的区块任务数 |
| `buffered_blocks` | 上述任务中已完成的数量；不含分片规范化缓冲 |
| `rpc_elements` | 共享客户端创建以来实际尝试的逻辑 RPC 元素数，包含重试 |
| `http_attempts` | 同一客户端的实际 HTTP 尝试次数 |
| `retries` | 额外 HTTP 尝试次数 |
| `http_429` | HTTP 429 响应数，包含终止尝试 |
| `in_flight` / `peak_in_flight` | 当前/峰值在途 HTTP 请求数 |
| `rpc_elements_per_second` | 元素尝试数除以客户端创建以来的单调时钟秒数 |

客户端计数包含前置探测，区块速率只统计本次新处理区块，不能混用两者。每个分片提交/跳过/恢复以及最终完成时报告进度；片内约 30 秒在区块完成边界报告一次。没有后台心跳，等待较早的有序结果、RPC 重试或磁盘提交时可能长时间没有新进度。采集完成日志之后单独执行完整性校验，ETA 不含该步骤及分析；全量校验本身可能昂贵。

## 离线可复现实验

```bash
PYTHONPATH=src python tools/benchmark_collection.py --blocks 120 --latency-ms 10 --concurrency 16 --qps 10000
```

脚本由随包 fixture 派生连续、唯一的合成区块/交易/receipts/logs，通过 `httpx.MockTransport` 为每个 HTTP 请求模拟固定延迟；不读取生产 URL，也不提供生产 URL 参数。临时输出使用 `TemporaryDirectory` 清理。串行和并发均使用同一全局 QPS，并先通过完整质量校验及逐表规范化内容一致性比较，再输出 JSON 中的 `synthetic_speedup`。

结果分别记录采集（含分片写盘）耗时/区块每秒、独立完整性校验耗时、实际 HTTP 次数、逻辑元素数和两个不同口径的峰值。`peak_in_flight` 是 RpcClient 中已获并发许可的完整 HTTP 尝试峰值，包含请求构建与响应处理；`transport_peak_in_flight` 只统计同时执行 MockTransport handler 的峰值。两者分别检查不超过配置并发数，无需相等；尤其零模拟延迟时，客户端峰值可能大于 handler 峰值。HTTP 尝试次数仍要求与模拟传输器实测次数相等。每次采集预期是一次链检查加每块两次 RPC，即 `1 + 2 * blocks` 次 HTTP；没有人为设定的 pytest 速度倍数门槛。性能会受到导入、文件系统和调度影响，输出是合成延迟实验，不代表主网吞吐、节点容量或实际速度承诺。

### 本次离线验证记录

Python 3.12，完整测试 **222 passed**，包含共享限流/冷却、延迟唤醒后不集中补发、有序写入、故障即时取消排队任务、原始错误保留、旧 manifest 恢复及基准脚本边界检查；编译检查通过。两个发现的并发边界问题均先以失败回归测试复现，再修复并复审。CLI 离线 demo/validate 通过，6区块、11交易、11回执、2日志，未连接真实节点。

| 合成实验 | 串行采集 | 并发采集 | 说明 |
| --- | --- | --- | --- |
| 120区块、每请求10ms延迟、QPS10000、并发16 | 3.0368秒 | 0.2229秒 | 约13.62倍；客户端/传输器峰值均由1增至16 |
| 120区块、0ms延迟、QPS200、并发32 | 1.5448秒 | 1.3642秒 | 受共享限速约束，并发并不自动提高允许的请求额度 |

两组均为串行/并发完整表内容一致且质量通过：120区块、220交易、220回执、40日志，各241次实际 HTTP/逻辑元素尝试。第二组并发客户端实测平均约176.66元素/秒，未绕过配置预算；该平均值不是对任意时间滑动窗口无突发的证明。两组完整性校验另行计时，不计入表中采集耗时。PyArrow/Parquet 导入与 schema 初始化、Store/HTTP 客户端创建在采集计时前完成。

这些结果仅证明本地模拟场景下能重叠网络等待并保留正确结果；不是主网负载、三个月规模、16GB RSS 上限、节点承载力或固定提速倍数的验证。真实吞吐和存储成本仍需在服务器短窗口实测。
