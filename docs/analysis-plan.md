# opBNB Mainnet Activity Analysis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 分析最近三个月 opBNB 主网的交易构成、活跃地址、头部项目、资金活动与持续性，形成可追溯的领导汇报材料。

**Architecture:** 使用用户提供的 archive API 获取链上明细，使用浏览器、项目官方资料及生态数据源补充归属和交叉校验。先完成接口能力和一天数据的验证，再扩展至三个月；内部调用追踪仅针对解释头部项目和关键资金流所必需的交易。基础统计、项目标签和汇报产物分别保存，以便重复计算和审查。

**Tech Stack:** Ethereum JSON-RPC、可验证的公开资料、结构化分析表；具体采集程序和分析运行时在接口验证后确定。本计划不新增或修改 opBNB/op-geth 协议代码。

## Global Constraints

- 统计范围为最近三个月，全部日期均纳入基础统计，不能以近一个月代替三个月详细分析。
- 按当前汇报日 2026-10-22 冻结窗口：北京时间 2026-07-22 00:00:00 至 2026-10-22 00:00:00，左闭右开，共 92 个完整自然日。
- 对应 UTC 窗口为 2026-07-21T16:00:00Z 至 2026-10-21T16:00:00Z。原始时间统一保存为 UTC，主报告按 Asia/Shanghai 分日。
- 与外部 UTC 日统计比较时，另生成相同 UTC 日边界的数据，不直接比较不同日边界。
- 接口凭据从用户指定的本地配置或环境变量读取，不写进报告、日志、原始响应样本或版本控制。
- 连接信息尚未提供；在取得连接信息前不声称完成节点能力验证或链上数据采集。
- 不提交 Git commit、不创建分支、不修改两个协议仓库；分析文件保存在本计划所在任务目录内。
- 当前阶段为数据分析执行计划，不包含采集器的软件实现；如需新增程序，先依据已验证接口细化实现与必要测试。
- 活跃地址不是独立自然人；自动化行为特征不直接等同于刷量或恶意行为。
- 未识别项目和不可可靠估值的代币保留原始信息，披露覆盖率，不强行归属或估值。

## Task 1: 验证 archive API 和冻结统计口径

**Files:** `analysis/config-summary.json`、`analysis/api-capabilities.md`、`analysis/metric-definitions.md`。

**Interfaces:** 消费用户提供的 API 连接方式、鉴权和已知限流；产出安全连接配置说明、日期和区块范围、接口能力及可行的数据获取路线。

- [ ] 取得 endpoint、鉴权方式、已知 QPS/并发及配额；不打印含密钥的完整 URL、请求头和异常请求对象。
- [ ] 在未获知限制前以单并发、每秒最多一次请求验证 `eth_chainId`、`eth_blockNumber`、`eth_getBlockByNumber`，确认目标为 opBNB Mainnet（预期 chain ID 204）。
- [ ] 在窗口起点和终点附近验证历史区块、交易及 receipt 的可访问性，通过区块时间定位左闭右开区块范围。
- [ ] 分别探测 JSON-RPC batch、`eth_getBlockReceipts`、`eth_getTransactionReceipt`、`eth_getLogs` 和历史 `eth_getCode`；记录方法不支持、日志跨度限制、响应大小限制及限流，不把 batch 元素数当成一次计费请求。
- [ ] 仅选取一笔交易探测 `debug_traceTransaction`，若不支持则记录替代路线；archive 状态保留能力与 trace 服务能力分开记录。
- [ ] 将每笔区块交易纳入总笔数，成功与失败分别计数；协议自动产生的系统交易单列，用户跨链存入交易不因交易类型相同而全部排除。
- [ ] 活跃指标同时保留全部非系统发送地址与成功非系统发送地址；报告主口径采用成功非系统发送地址去重，并明确失败交易及合约账户、中继的处理。

**验收:** 不泄露凭据；链、窗口和历史覆盖正确；每项方法有实际验证结果；不能完成的指标能对应到具体缺失能力。

## Task 2: 一天端到端试采集与三个月成本估算

**Files:** `analysis/data-manifest.json`、`analysis/api-capabilities.md`、`analysis/quality-checks.md`。

**Interfaces:** 消费 Task 1 的连接限制和数据口径；产出一天可核验的数据、吞吐量和完整窗口的采集方案。

- [ ] 选择窗口内最近一个完整北京时间自然日，读取全部区块和完整交易；保存区块号、区块哈希、父哈希、时间、交易哈希、from、to、value、input 和交易类型。
- [ ] 获取 receipt，保留 status、gasUsed、effectiveGasPrice、L1 费用相关字段和日志；批量 receipt 不支持时退回逐笔请求，不假定 batch 可绕过配额。
- [ ] 为采集分区记录成功范围、失败范围和校验状态；重试采用退避，支持中断后从未完成分区继续，最终按交易哈希去重。
- [ ] 核对区块连续性、父哈希衔接、区块内交易数和已保存交易数、receipt 对应关系、日志重复与缺失。
- [ ] 实测每秒请求、每秒处理交易、响应字节量及存储量，依据各月代表性区块交易密度估算三个月规模，说明估计区间和高峰日的不确定性。
- [ ] 结合用户已知配额和计费规则记录预计资源消耗；如现有配额不足，先缩减全量 trace 等可选内容，保留三个月基础统计目标，不自行购买服务或扩大付费套餐。

**验收:** 一天区块及交易、receipt 无未解释缺口；费用字段已核对；完整窗口有基于实测的请求量、耗时与存储估计，不能以公共 RPC 常见性能代替实测。

## Task 3: 三个月基础统计与头部交易对象

**Files:** `analysis/data-manifest.json`、`analysis/daily-metrics.csv`、`analysis/contract-ranking.csv`、`analysis/sender-ranking.csv`。

**Interfaces:** 消费经过验证的数据获取方案和定义；产出逐日、逐周、逐月及全窗口指标，并保留可追溯的交易证据。

- [ ] 采集完整 92 天的区块、交易及 receipt，按 Task 2 的完整性条件逐分区验证。
- [ ] 统计每日总交易、系统交易、非系统成功与失败交易、发送地址数、成功发送地址数，以及周/月去重活跃地址。不能将每日活跃地址简单求和作为月活。
- [ ] 统计主要直接调用目标、方法选择器、交易数、成功数、独立发送地址、手续费和每日变化；创建交易单独统计。
- [ ] 技术主分类采用互斥规则：系统交易、创建交易、可确认的普通原生资产转账、合约交互和未分类；转账、授权、兑换、跨链及游戏等业务标签另行记录，标明是否允许多标签。
- [ ] 对高贡献目标核验相关历史区块的代码、代理与实现归属，不仅凭 input 为空或当前代码状态判断交易性质，不仅凭四字节方法选择器认定业务。
- [ ] 输出 Top 发送地址的交易贡献、目标和方法分布、活跃天数、小时分布及发送间隔特征；对中继、批处理和智能账户场景保留限制说明。
- [ ] 汇报最近 7 天对前 7 天、最近 30 天对前 30 天及全窗口趋势；不将窗口两端的不足整月直接作为整月环比。

**验收:** 92 天都有指标或明确缺失标记；分类总数与总交易数一致；成功与失败之和可核对；排名区分交易贡献和地址覆盖。

## Task 4: 头部合约归属和项目级贡献

**Files:** `analysis/project-labels.csv`、`analysis/project-ranking.csv`。

**Interfaces:** 消费合约、方法和地址排名；产出有证据的项目归属、行业分类及覆盖率。

- [ ] 合并交易数、地址数和手续费三个维度的 Top 30～50 合约作为首轮核验集合，计算覆盖的全网非系统成功交易比例；覆盖不足时按贡献递补并披露最终覆盖率。
- [ ] 每个地址记录 address、project、business_category、contract_role、evidence_url、checked_at、confidence 和适用区块范围；可信度为已确认、较可信、未知。
- [ ] 优先核对项目官方部署资料及认证源码，以 DappBay 和浏览器标签补充线索；未知地址保留未知。
- [ ] 同项目合约归并，项目独立地址用集合去重，不将合约级独立地址数直接求和。
- [ ] 主榜以可确认的直接调用归属保证一笔交易只归入一个项目或未知；路由器与下游项目的交互覆盖另表展示，不与主榜相加，必要时对关键交易补 trace。
- [ ] 分别展示项目交易占比、项目内独立发送地址、手续费贡献、增长和变化；说明同一地址可参与多个项目，项目地址覆盖之和可超过全网去重地址数。

**验收:** 已确认归属有可访问证据；主榜不重复计数；未知比例和路由覆盖限制可见；业务分类与原始调用行为能相互解释。

## Task 5: 资金、成本、集中度和留存

**Files:** `analysis/fund-activity.csv`、`analysis/retention-concentration.csv`、`analysis/quality-checks.md`。

**Interfaces:** 消费交易、receipt、项目映射及可核验的价格和外部指标；产出分口径资金与活跃质量指标。

- [ ] 分别统计成功交易的顶层 BNB value 与经确认代币的 Transfer 事件金额，披露是否覆盖内部 BNB 转账；铸造和销毁单列，排除失败交易的无效转移，不把流转额称为独立经济成交额。
- [ ] 代币白名单记录地址、精度、价格来源、价格时间粒度；对有可靠价格的资产按交易时段价格折算美元，其余按原币展示，同时披露有价格覆盖的事件比例及资产清单。
- [ ] DEX 现货成交额、衍生品名义成交额、转账额和 TVL 分表展示；多跳兑换避免将所有跳数相加为终端用户成交额，覆盖不足时采用已注明范围的公开统计。
- [ ] 官方桥和第三方桥分别识别流入、流出及完成状态；在只有 L2 数据时明确流出按发起还是完成计数。如需核验 BSC 最终完成量，另需 L1 数据源，不将提现发起直接称为已完成流出。
- [ ] 计算日手续费总额、每笔中位数和 P90，并核对 receipt 的 L1 与 L2 费用，避免漏计或重复；费用支出不直接称为运营利润。
- [ ] 统计 Top 1/5/10 项目交易占比，以及 Top 1% 成功非系统发送地址的交易占比；标明交易和地址分母。用去除头部项目后的交易趋势观察其余生态。
- [ ] 以窗口内首次成功活动日期形成地址 cohort，统计次日、第 7 日和次周留存，只纳入观察期已成熟的 cohort；没有窗口前完整历史核验时称窗口内首次出现地址，不称全链新用户。
- [ ] 对主要波动日期拆解项目和方法贡献，并核验公开活动信息；区分已证实原因、关联线索和未解释波动。

**验收:** 金额口径之间不混加；未知价格和内部转账缺口明确；未成熟 cohort 不记为流失；异常自动化特征有证据且不等同于真实人数估计。

## Task 6: 数据审查与领导汇报

**Files:** `analysis/quality-checks.md`、`report/executive-summary.md`、`report/report-outline.md`。

**Interfaces:** 消费上述全量指标和证据；产出一页摘要、6～8 页报告提纲及可复算附件。

- [ ] 对普通日、峰值日和低谷日各抽取至少一天，与浏览器或独立统计源按相同日边界比较，记录交易数和地址数差异及解释。
- [ ] 每个头部项目至少抽查 3 笔代表性交易，核对调用目标、执行状态、方法与日志；业务存在多种主要行为时分别抽查。
- [ ] 第一页展示日均交易、日均成功活跃发送地址、窗口去重活跃地址、近期变化、Top 5 项目贡献及资金活动摘要。
- [ ] 后续页面依次呈现：整体趋势；交易业务构成；头部项目；高频发送方；资金与费用；留存与集中度；管理结论及数据边界。内容接近时合并至 6～8 页。
- [ ] 每个核心结论关联统计窗口、指标定义、来源和附件；将观察事实与推断分开，避免用理论 TPS 替代实际使用量。
- [ ] 检查交易、活跃、项目归属、资金、成本、留存、集中度和增长来源均有结果或明确缺口；输出所有缺失数据及其对结论的影响。

**验收:** 读者能独立回答规模、用途、贡献者和持续性四个问题；关键结论可追溯；不能确认的内容没有被包装成确定事实。
